## 1. 프로젝트 비전

### 1.1 우리는 왜 이것을 만드는가?

**"오늘 한 게 없다고? 무무는 봤는데."**

현대인들은 거창한 목표를 세우는 것부터 부담스러워합니다. Polaris는 사용자가 직접 목표를 세우지 않아도, **AI 캐릭터가 먼저 말을 걸고 작은 미션을 제안**하여 루틴의 시작 이유를 만들어주는 서비스입니다.

### 1.2 핵심 가치 제안

```
문제: "오늘 뭘 해야 할지 모르겠다. 목표 세우기부터 부담스럽다."
해결: 캐릭터가 먼저 말을 걸고, AI가 지금 할 수 있는 작은 미션을 제안한다.
결과: 작은 행동이 별조각이 되고, 캐릭터와의 관계가 쌓인다.
```

### 1.3 제품 포지셔닝

- ❌ 자기계발 앱이 아닙니다
- ❌ 할 일 관리 도구가 아닙니다
- ✅ **작은 일상을 같이 살아주는 캐릭터 앱**입니다

## 6. 아키텍처 원칙

### 6.1 설계 원칙

#### 1) 단일 트랜잭션 오너 원칙
```
각 비즈니스 트랜잭션은 하나의 모듈이 소유한다.
다른 모듈의 데이터 변경은 이벤트로 전파한다.

예시:
- 미션 완료 트랜잭션 오너: mission 모듈
- 별조각 지급은 MissionCompletedEvent로 전파
- economy 모듈이 이벤트 구독하여 별조각 지급
```

#### 2) 읽기/쓰기 통신 분리
```
읽기: gRPC (동기, 빠른 응답)
쓰기: Spring Event (비동기, 결합도 낮음)
```

#### 3) Fail-Safe 설계
```
AI 생성 실패 → seed 문구 사용
알림 발송 실패 → 재시도 큐 적재
이벤트 처리 실패 → Dead Letter Queue
```

### 6.2 모듈 경계 규칙

| 모듈 | 핵심 책임 | 소유 데이터 |
|------|----------|------------|
| **gateway** | REST API 제공, gRPC 라우팅 | 없음 (stateless) |
| **user** | 인증, 프로필, 설문, **별조각 지갑** | users, user_profiles, onboarding_surveys, **star_piece_wallets**, **star_piece_transactions** |
| **character** | 캐릭터 생성, 상태 관리, 돌봄, **캐릭터 카드 생성, 공유 링크 관리** | character_types, character_assets, characters, character_states, character_care_logs, **share_events** |
| **mission** | 미션 생성, 제안, 완료, 거절 | mission_templates, missions, mission_interactions |
| **item** | 아이템 카탈로그, 구매, 장착 | item_catalog, user_items |
| **ai** | AI 미션 생성, 프롬프트 관리 | ai_generation_logs, prompt_templates |
| **notification** | 알림 템플릿 관리, 알림 발송, 알림 설정 | notification_templates, notification_logs, user_notification_settings |

**통신 규칙:**

| 규칙 | 설명 | 예외 |
|------|------|------|
| 직접 DB 접근 금지 | 각 모듈은 자신의 DB만 접근 | 없음 |
| 도메인 이벤트 발행 | 상태 변경 시 이벤트 발행 | 읽기 전용 작업 |
| gRPC는 읽기만 | 쓰기는 이벤트 사용 | 없음 |
| Proto 버전 관리 | 하위 호환성 유지 | 없음 |

## 7. 핵심 비즈니스 플로우

### 7.1 미션 완료 플로우 (트랜잭션 예시)

```
[사용자] 미션 완료 버튼 클릭
    ↓
[gateway] POST /api/missions/{id}/complete
    ↓
[mission 모듈] ← 트랜잭션 오너
    1. 미션 상태 COMPLETED 저장
    2. 완료 질문 1개 반환
    3. MissionCompletedEvent 발행 ← 트랜잭션 커밋 후
    ↓
[user 모듈] ← 이벤트 구독
    - 별조각 +10 지급
    - StarPieceEarnedEvent 발행
    ↓
[character 모듈] ← 이벤트 구독
    - affection +5 증가
    - 상태 이미지 갱신
    ↓
[notification 모듈] ← 이벤트 구독
    - Web Push 알림 발송: "별조각 +10 획득!"
```

### 7.2 AI 미션 생성 플로우 (비동기)

```
[스케줄러] 매일 새벽 3시
    ↓
[ai 모듈]
    1. 활성 사용자 목록 조회 (user 모듈 gRPC)
    2. 각 사용자별 컨텍스트 수집
       - 설문 답변 (user 모듈 gRPC)
       - 최근 완료/거절 미션 (mission 모듈 gRPC)
       - 캐릭터 상태 (character 모듈 gRPC)
    3. Spring AI로 미션 생성 (Gemini/GPT)
    4. Redis에 캐시 저장 (key: user:{id}:missions:today)
    5. 생성 실패 시 seed 문구 사용
    ↓
[사용자] 앱 접속
    ↓
[mission 모듈]
    1. Redis에서 미션 조회
    2. 없으면 동기 생성 (fallback)
    3. 미션 1개 반환
```

## 8. 데이터 정합성 전략

### 8.1 이벤트 기반 최종 일관성

| 시나리오 | 처리 방식 |
|----------|----------|
| 이벤트 발행 실패 | 트랜잭션 롤백 (Transactional Outbox 패턴) |
| 이벤트 처리 실패 | 재시도 큐 (Redis) + 스케줄러 재처리 |
| 중복 이벤트 | Idempotency Key로 중복 방지 |
| 순서 보장 | 이벤트에 sequence 포함 |

### 8.2 보상 트랜잭션

```
예시: 별조각 지급 후 character 상태 업데이트 실패

1. user 모듈: 별조각 +10 성공
2. character 모듈: affection +5 실패
3. CharacterUpdateFailedEvent 발행
4. user 모듈: 별조각 -10 보상 트랜잭션
5. gateway: 관리자 알림 발송 (Slack/Email)
```

## 10. 리스크 관리

### 10.1 기술 리스크

| 리스크 | 영향도 | 완화 방안 |
|--------|--------|----------|
| AI API 장애 | 🔴 높음 | seed 문구 fallback, 캐시 활용 |
| gRPC 통신 장애 | 🟡 중간 | Circuit Breaker, 재시도 |
| 이벤트 유실 | 🟡 중간 | Transactional Outbox 패턴 |
| Redis 장애 | 🟢 낮음 | DB 조회로 fallback |

### 10.2 일정 리스크

| 리스크 | 확률 | 완화 방안 |
|--------|------|----------|
| AI 통합 지연 | 30% | Spring AI 사전 학습, 샘플 코드 준비 |
| gRPC 디버깅 어려움 | 40% | 로깅 강화, Postman gRPC 활용 |
| 이벤트 처리 복잡도 | 50% | 핵심 플로우만 이벤트 적용 |
