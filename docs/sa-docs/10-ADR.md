## ADR-001: 모듈러 모놀리스 아키텍처 채택

**상태**: Accepted

**날짜**: 2026-05-14

### 컨텍스트

Polaris MVP는 초기 단계 프로젝트로, 빠른 개발과 배포가 필요하지만 향후 확장성도 고려해야 합니다. 아키텍처 선택지는 다음과 같습니다:

1. **순수 모놀리스**: 모든 기능이 하나의 애플리케이션
2. **모듈러 모놀리스**: 논리적으로 분리된 모듈, 물리적으로는 하나의 애플리케이션
3. **MSA (Microservices)**: 각 서비스가 독립적으로 배포

### 고려한 대안

#### A. 순수 모놀리스
- **장점**: 가장 빠른 개발, 단순한 배포
- **단점**: 코드 결합도 높음, 확장 어려움, MSA 전환 시 대규모 리팩토링 필요

#### B. 모듈러 모놀리스
- **장점**: 논리적 분리로 결합도 낮춤, MSA 전환 용이, 개발 속도 빠름
- **단점**: 모듈 경계 설계 필요, 순수 모놀리스보다 복잡

#### C. MSA
- **장점**: 완전한 독립성, 확장성 최고
- **단점**: 개발/운영 복잡도 높음, 초기 오버헤드 큼, 소규모 팀에 부적합

### 결정

**모듈러 모놀리스 아키텍처를 채택합니다.**

10개 모듈로 구성:
- Gateway Module
- User Module
- Character Module
- Item Module
- Mission Module
- AI Module
- Notification Module
- Achievement Module (MVP 이후)
- Analytics Module (MVP 이후)
- Operation Module

### 근거

1. **빠른 MVP 출시**: 단일 애플리케이션으로 배포 간소화
2. **향후 MSA 전환 대비**: 모듈 경계가 명확하여 전환 용이
3. **개발 생산성**: 모듈 간 직접 호출로 개발 속도 유지
4. **운영 부담 최소화**: 단일 서버 관리, 네트워크 레이턴시 없음
5. **팀 규모 적합**: 소규모 팀에서 관리 가능한 복잡도

### 결과 (긍정)

- ✅ 빠른 개발 및 배포 가능
- ✅ 모듈 간 명확한 경계 유지
- ✅ 트랜잭션 관리 단순
- ✅ 디버깅 용이

### 결과 (부정/리스크)

- ⚠️ 모듈 간 의존성 관리 필요
- ⚠️ 단일 장애점 (SPOF)
- ⚠️ 수평 확장 제한

### 재검토 조건

- DAU 10,000명 이상 도달 시
- 특정 모듈의 트래픽이 전체의 80% 이상 차지 시
- 모듈 간 결합도 문제로 개발 속도 저하 시

## ADR-002: 모듈 간 FK 제약조건 제거

**상태**: Accepted

**날짜**: 2026-05-14

### 컨텍스트

모듈러 모놀리스에서 모듈 간 데이터 참조 시 FK 제약조건 사용 여부를 결정해야 합니다.

### 고려한 대안

#### A. 모든 관계에 FK 사용
- **장점**: 데이터 무결성 보장, 참조 무결성 자동 검증
- **단점**: MSA 전환 시 FK 제거 필요, 모듈 간 강한 결합

#### B. 모듈 내부만 FK 사용
- **장점**: 모듈 독립성 유지, MSA 전환 용이, 데이터 무결성은 애플리케이션 레벨에서 관리
- **단점**: 참조 무결성 검증 로직 필요, 고아 레코드 발생 가능성

#### C. FK 전혀 사용 안 함
- **장점**: 완전한 독립성
- **단점**: 모듈 내부 무결성도 애플리케이션에서 관리, 복잡도 증가

### 결정

**같은 모듈 내에서만 FK 제약조건을 사용하고, 다른 모듈 간에는 ID만 저장합니다.**

예시:
```sql
-- ✅ 같은 모듈 내 (Character Module)
user_characters.character_type_id → character_types.id (FK 있음)

-- ❌ 다른 모듈 간 (Character → User)
user_characters.user_id → users.id (FK 없음, ID만 저장)
```

### 근거

1. **MSA 전환 대비**: 모듈이 독립적인 데이터베이스로 분리될 때 FK 제거 불필요
2. **모듈 독립성**: 한 모듈의 스키마 변경이 다른 모듈에 영향 없음
3. **배포 독립성**: 향후 모듈별 독립 배포 가능
4. **참조 무결성**: 애플리케이션 레벨에서 검증 (Service Layer)

### 결과 (긍정)

- ✅ 모듈 간 느슨한 결합
- ✅ MSA 전환 시 마이그레이션 간소화
- ✅ 모듈별 독립적인 스키마 관리

### 결과 (부정/리스크)

- ⚠️ 참조 무결성 검증 로직 필요
- ⚠️ 고아 레코드 발생 가능성 (정기 정합성 체크 필요)
- ⚠️ 개발자가 참조 관계를 명확히 이해해야 함

### 재검토 조건

- 고아 레코드 문제가 빈번히 발생 시
- 참조 무결성 검증 로직이 과도하게 복잡해질 시

## ADR-003: 이벤트 기반 아키텍처 MVP 제외

**상태**: Accepted

**날짜**: 2026-05-14

### 컨텍스트

모듈 간 통신 방식을 결정해야 합니다. 이벤트 기반 아키텍처는 느슨한 결합을 제공하지만 복잡도가 증가합니다.

### 고려한 대안

#### A. 직접 호출 방식
- **장점**: 구현 단순, 빠른 개발, 동기 처리로 디버깅 용이
- **단점**: 모듈 간 결합도 높음, MSA 전환 시 수정 필요

#### B. 이벤트 기반 (Outbox/Inbox Pattern)
- **장점**: 느슨한 결합, 트랜잭션 보장, MSA 전환 용이
- **단점**: 복잡도 높음, 최종 일관성, 디버깅 어려움

#### C. 메시지 큐 (Kafka, RabbitMQ)
- **장점**: 완전한 비동기, 확장성 높음
- **단점**: 인프라 추가, 운영 부담, MVP에 과도한 복잡도

### 결정

**MVP 단계에서는 직접 호출 방식을 사용하고, 이벤트 기반 아키텍처는 별도 문서(O1)로 작성하여 향후 적용을 대비합니다.**

예시:
```java
// MVP: 직접 호출
@Transactional
public void completeMission(Long missionId) {
    mission.setStatus(COMPLETED);
    missionRepository.save(mission);
    
    // 직접 호출
    starPieceService.earnStarPieces(userId, reward);
    characterService.increaseAffection(characterId, 5);
}
```

### 근거

1. **빠른 MVP 출시**: 이벤트 인프라 구축 시간 절약
2. **개발 복잡도 최소화**: 동기 처리로 디버깅 용이
3. **트랜잭션 단순화**: 단일 트랜잭션으로 원자성 보장
4. **향후 전환 대비**: 모듈 인터페이스를 명확히 정의하여 전환 용이

### 결과 (긍정)

- ✅ 빠른 개발 및 배포
- ✅ 단순한 트랜잭션 관리
- ✅ 디버깅 용이
- ✅ 운영 부담 최소화

### 결과 (부정/리스크)

- ⚠️ 모듈 간 결합도 높음
- ⚠️ MSA 전환 시 리팩토링 필요
- ⚠️ 확장성 제한

### 재검토 조건

- 트래픽 증가로 성능 문제 발생 시
- 모듈 간 결합도로 인한 개발 속도 저하 시
- MSA 전환 준비 시점

## ADR-004: 알림 도메인 독립 모듈 분리

**상태**: Accepted

**날짜**: 2026-05-14

### 컨텍스트

알림 기능을 어느 모듈에 포함시킬지 결정해야 합니다. 초기에는 Gateway Module에 포함하는 것을 고려했으나, 알림은 독립적인 도메인 로직을 가집니다.

### 고려한 대안

#### A. Gateway Module에 포함
- **장점**: 모듈 수 감소, 단순한 구조
- **단점**: Gateway의 책임 과다, 알림 로직과 라우팅 로직 혼재

#### B. Notification Module로 분리
- **장점**: 단일 책임 원칙, 독립적인 확장 가능, 명확한 도메인 경계
- **단점**: 모듈 수 증가

#### C. 각 모듈에서 직접 발송
- **장점**: 모듈 독립성 최대
- **단점**: 알림 로직 중복, 일관성 없는 알림 관리

### 결정

**Notification Module로 독립 분리합니다.**

포함 테이블:
- `device_tokens`: 디바이스 토큰 관리
- `notification_settings`: 사용자별 알림 설정
- `notification_logs`: 알림 전송 이력

### 근거

1. **단일 책임 원칙**: 알림 발송과 설정 관리는 독립적인 도메인
2. **재사용성**: 모든 모듈에서 알림 서비스 활용
3. **확장성**: 향후 알림 채널 추가 시 독립적으로 확장
4. **모니터링**: 알림 전송 이력을 중앙에서 관리

### 결과 (긍정)

- ✅ 명확한 도메인 경계
- ✅ 알림 로직 중앙 관리
- ✅ 독립적인 확장 가능
- ✅ 일관된 알림 정책 적용

### 결과 (부정/리스크)

- ⚠️ 모듈 수 증가
- ⚠️ 모듈 간 호출 필요

### 재검토 조건

- 알림 기능이 과도하게 단순해져서 독립 모듈이 불필요해질 시

## ADR-005: 아이템 도메인 독립 모듈 분리

**상태**: Accepted

**날짜**: 2026-05-14

### 컨텍스트

아이템(스킨, 배경, 소모품) 관리를 Character Module에 포함시킬지, 독립 모듈로 분리할지 결정해야 합니다.

### 고려한 대안

#### A. Character Module에 포함
- **장점**: 캐릭터와 아이템이 밀접한 관계, 모듈 수 감소
- **단점**: Character Module 책임 과다, 아이템 상점 로직 혼재

#### B. Item Module로 분리
- **장점**: 단일 책임 원칙, 상점 로직 독립 관리, 확장 용이
- **단점**: 모듈 수 증가, 모듈 간 호출 필요

### 결정

**Item Module로 독립 분리합니다.**

포함 테이블:
- `items`: 아이템 마스터 데이터
- `user_items`: 사용자 보유 아이템
- `item_purchase_logs`: 구매 이력

### 근거

1. **단일 책임 원칙**: 아이템 상점과 캐릭터 관리는 별개 도메인
2. **확장성**: 향후 아이템 종류 추가 시 독립적으로 확장
3. **비즈니스 로직 분리**: 구매, 장착, 사용 로직을 명확히 분리
4. **재사용성**: 아이템은 여러 캐릭터에서 공통 사용 가능

### 결과 (긍정)

- ✅ 명확한 도메인 경계
- ✅ 상점 로직 독립 관리
- ✅ 아이템 확장 용이
- ✅ Character Module 책임 경량화

### 결과 (부정/리스크)

- ⚠️ 모듈 간 호출 필요 (아이템 장착 시)
- ⚠️ 트랜잭션 경계 고려 필요

### 재검토 조건

- 아이템 기능이 과도하게 단순해질 시
- Character Module과의 결합도가 너무 높아질 시

## ADR-006: 미션 도메인과 AI 모듈 분리

**상태**: Accepted

**날짜**: 2026-05-14

### 컨텍스트

미션 생성 시 AI가 필요하지만, 미션 도메인 로직과 AI 로직을 어떻게 분리할지 결정해야 합니다.

### 고려한 대안

#### A. Mission Module에 AI 로직 포함
- **장점**: 미션 생성 로직이 한 곳에 집중
- **단점**: AI 로직과 도메인 로직 혼재, AI 교체 시 Mission Module 수정 필요

#### B. AI Module 분리 (테이블 없음, 로직만)
- **장점**: AI 로직 독립 관리, AI 교체 용이, 재사용 가능
- **단점**: 모듈 간 호출 필요

#### C. AI를 외부 서비스로 분리
- **장점**: 완전한 독립성
- **단점**: MVP에 과도한 복잡도, 네트워크 레이턴시

### 결정

**AI Module을 독립 모듈로 분리하되, 데이터베이스 테이블은 없이 로직만 포함합니다.**

AI Module 책임:
- AI API 호출 (OpenAI, Claude 등)
- 프롬프트 생성
- Fallback 문구 관리
- RAG 정책 적용

Mission Module 책임:
- 미션 템플릿 관리
- 미션 추천 알고리즘
- 미션 상태 관리
- 보상 지급

### 근거

1. **관심사 분리**: AI 로직과 도메인 로직 명확히 분리
2. **AI 교체 용이**: AI 제공사 변경 시 AI Module만 수정
3. **재사용성**: 다른 모듈에서도 AI 서비스 활용 가능
4. **테스트 용이**: AI 로직을 Mock으로 대체하여 테스트

### 결과 (긍정)

- ✅ AI 로직 독립 관리
- ✅ AI 제공사 교체 용이
- ✅ 테스트 용이 (Mock 사용)
- ✅ 재사용 가능

### 결과 (부정/리스크)

- ⚠️ 모듈 간 호출 필요
- ⚠️ AI API 장애 시 Fallback 처리 필요

### 재검토 조건

- AI 기능이 과도하게 복잡해져서 독립 서비스가 필요해질 시
- 다른 모듈에서 AI 사용이 없어질 시

## ADR-007: REST API 설계 원칙

**상태**: Accepted

**날짜**: 2026-05-14

### 컨텍스트

API 설계 방식을 결정해야 합니다. REST, GraphQL, gRPC 등 다양한 선택지가 있습니다.

### 고려한 대안

#### A. REST API
- **장점**: 표준화, 캐싱 용이, 도구 풍부, 학습 곡선 낮음
- **단점**: Over-fetching/Under-fetching, 엔드포인트 증가

#### B. GraphQL
- **장점**: 유연한 쿼리, Over-fetching 방지
- **단점**: 캐싱 어려움, 학습 곡선 높음, 복잡도 증가

#### C. gRPC
- **장점**: 성능 우수, 타입 안전
- **단점**: 브라우저 지원 제한, 디버깅 어려움

### 결정

**REST API를 채택하고, 다음 원칙을 따릅니다:**

1. **자원 중심 설계**: URL은 자원을 나타냄 (동사 사용 금지)
   - ✅ `GET /missions/current`
   - ❌ `GET /getMission`

2. **HTTP 메서드 의미 준수**:
   - GET: 조회
   - POST: 생성
   - PUT: 전체 수정
   - PATCH: 부분 수정
   - DELETE: 삭제

3. **상태 코드 명확히 사용**:
   - 200: 성공
   - 201: 생성 성공
   - 400: 클라이언트 오류
   - 401: 인증 실패
   - 403: 권한 없음
   - 404: 리소스 없음
   - 500: 서버 오류

4. **일관된 응답 형식**:
   ```json
   {
     "success": true,
     "data": {},
     "error": null,
     "timestamp": "2026-05-14T10:00:00Z"
   }
   ```

5. **버저닝**: URL에 버전 포함 (`/v1/...`)

### 근거

1. **표준화**: REST는 업계 표준으로 널리 사용됨
2. **캐싱**: HTTP 캐싱 메커니즘 활용 가능
3. **도구 지원**: Postman, Swagger 등 풍부한 도구
4. **학습 곡선**: 팀원 모두 익숙한 기술
5. **프론트엔드 호환성**: 웹, iOS, Android 모두 지원

### 결과 (긍정)

- ✅ 표준화된 API 설계
- ✅ 캐싱 전략 적용 용이
- ✅ 디버깅 및 테스트 용이
- ✅ 문서화 도구 활용 가능

### 결과 (부정/리스크)

- ⚠️ Over-fetching 가능성
- ⚠️ 엔드포인트 수 증가

### 재검토 조건

- Over-fetching으로 인한 성능 문제 발생 시
- 복잡한 쿼리 요구사항 증가 시

## ADR-008: Cursor 기반 페이징 채택

**상태**: Accepted

**날짜**: 2026-05-14

### 컨텍스트

목록 조회 API에서 페이징 방식을 결정해야 합니다.

### 고려한 대안

#### A. Offset 기반 페이징
- **장점**: 구현 단순, 페이지 번호 직접 접근 가능
- **단점**: 대량 데이터에서 성능 저하, 중복/누락 가능성

```
GET /missions/history?page=2&size=20
```

#### B. Cursor 기반 페이징
- **장점**: 성능 우수, 중복/누락 방지, 실시간 데이터 변경에 안전
- **단점**: 페이지 번호 직접 접근 불가, 구현 복잡

```
GET /missions/history?cursor=eyJpZCI6MTIzNDR9&limit=20
```

#### C. Keyset 페이징
- **장점**: 성능 우수
- **단점**: 정렬 키 변경 시 복잡, 구현 어려움

### 결정

**Cursor 기반 페이징을 채택합니다.**

응답 형식:
```json
{
  "data": {
    "items": [...],
    "pagination": {
      "nextCursor": "eyJpZCI6MTIzNDR9",
      "hasMore": true
    }
  }
}
```

### 근거

1. **성능**: 인덱스 활용으로 빠른 조회
2. **안정성**: 실시간 데이터 변경에도 중복/누락 없음
3. **확장성**: 대량 데이터에서도 일정한 성능
4. **모바일 친화적**: 무한 스크롤에 적합

### 결과 (긍정)

- ✅ 우수한 성능
- ✅ 중복/누락 방지
- ✅ 무한 스크롤 구현 용이
- ✅ 대량 데이터 처리 가능

### 결과 (부정/리스크)

- ⚠️ 페이지 번호 직접 접근 불가
- ⚠️ 구현 복잡도 증가

### 재검토 조건

- 페이지 번호 직접 접근이 필수 요구사항이 될 시
- Cursor 구현의 복잡도가 과도해질 시

## ADR-009: AI 생성 문구 Fallback 전략

**상태**: Accepted

**날짜**: 2026-05-14

### 컨텍스트

AI API 호출 실패 시 사용자 경험을 유지하기 위한 전략이 필요합니다.

### 고려한 대안

#### A. AI 실패 시 에러 반환
- **장점**: 구현 단순
- **단점**: 사용자 경험 저하, 서비스 중단

#### B. Fallback 문구 사용
- **장점**: 서비스 연속성 유지, 사용자 경험 보장
- **단점**: Fallback 문구 관리 필요

#### C. 캐싱된 이전 문구 재사용
- **장점**: 자연스러운 문구
- **단점**: 맥락에 맞지 않을 수 있음

### 결정

**Fallback 문구 DB를 구축하고, AI 실패 시 자동으로 사용합니다.**

Fallback 전략:
1. AI API 호출 (Timeout: 3초)
2. 실패 시 Fallback 문구 사용
3. `fallback_used` 플래그 기록
4. 운영팀에 알림 발송

Fallback 문구 구성:
- 캐릭터별 (노바, 무무, 쪼리)
- 카테고리별 (7개 미션 카테고리)
- 상황별 (제안, 질문, 반응, 거절)

### 근거

1. **서비스 연속성**: AI 장애 시에도 서비스 제공
2. **사용자 경험**: 에러 없이 자연스러운 흐름 유지
3. **비용 최적화**: Fallback 우선 사용으로 AI API 비용 절감
4. **안정성**: AI API 의존도 낮춤

### 결과 (긍정)

- ✅ 서비스 안정성 향상
- ✅ AI 장애 시에도 서비스 제공
- ✅ 비용 절감 (Fallback 우선 사용 가능)
- ✅ 사용자 경험 보장

### 결과 (부정/리스크)

- ⚠️ Fallback 문구 관리 필요
- ⚠️ AI 생성 문구보다 품질 낮을 수 있음
- ⚠️ 반복적인 문구로 느껴질 수 있음

### 재검토 조건

- Fallback 사용률이 50% 이상일 시
- 사용자 피드백에서 반복적인 문구 불만이 증가할 시

## ADR-010: 캐릭터 상태 자동 감소 정책

**상태**: Accepted

**날짜**: 2026-05-14

### 컨텍스트

캐릭터 상태(fullness, energy, affection)를 자동으로 감소시켜 사용자의 지속적인 참여를 유도해야 합니다.

### 고려한 대안

#### A. 실시간 감소 (매 분마다)
- **장점**: 정확한 상태 반영
- **단점**: 서버 부하 높음, 데이터베이스 쓰기 빈번

#### B. 배치 감소 (1시간마다)
- **장점**: 서버 부하 낮음, 데이터베이스 쓰기 최소화
- **단점**: 상태 반영 지연

#### C. 조회 시 계산 (Lazy Evaluation)
- **장점**: 서버 부하 최소, 데이터베이스 쓰기 없음
- **단점**: 조회 시 계산 필요, 알림 발송 어려움

### 결정

**배치 감소 방식을 채택합니다 (1시간마다).**

감소 정책:
- **fullness**: 1시간마다 -5 (20시간 후 0)
- **energy**: 1시간마다 -3 (33시간 후 0)
- **affection**: 1시간마다 -1 (100시간 후 0)

상태 등급:
- **GOOD**: 70~100
- **NORMAL**: 40~69
- **BAD**: 1~39
- **CRITICAL**: 0

### 근거

1. **서버 부하**: 1시간 주기로 부하 분산
2. **사용자 경험**: 1시간 단위는 사용자가 인지 가능한 적절한 주기
3. **알림 발송**: 상태 변경 시점에 알림 발송 가능
4. **데이터베이스**: 쓰기 빈도 최소화

### 결과 (긍정)

- ✅ 서버 부하 최소화
- ✅ 적절한 게임 밸런스
- ✅ 알림 발송 가능
- ✅ 데이터베이스 부하 낮음

### 결과 (부정/리스크)

- ⚠️ 1시간 단위로만 상태 변경
- ⚠️ 배치 작업 실패 시 상태 갱신 지연

### 재검토 조건

- 사용자 피드백에서 상태 감소가 너무 빠르거나 느리다는 의견이 많을 시
- 서버 부하가 충분히 낮아서 더 짧은 주기가 가능해질 시

## ADR-011: 별조각 경제 시스템 설계

**상태**: Accepted

**날짜**: 2026-05-14

### 컨텍스트

별조각(게임 내 화폐)의 획득과 소비 밸런스를 설계해야 합니다. 사용자가 지속적으로 참여하면서도 과도한 그라인딩을 방지해야 합니다.

### 고려한 대안

#### A. 관대한 경제 (획득 > 소비)
- **장점**: 사용자 만족도 높음, 진입 장벽 낮음
- **단점**: 게임 수명 짧음, 목표 달성 후 이탈

#### B. 엄격한 경제 (획득 < 소비)
- **장점**: 장기 플레이 유도, 과금 유도 가능
- **단점**: 사용자 불만, 진입 장벽 높음

#### C. 균형 경제 (획득 ≈ 소비)
- **장점**: 적절한 도전 과제, 장기 플레이 유도
- **단점**: 밸런싱 어려움

### 결정

**균형 경제를 채택하되, 초기에는 약간 관대하게 설정합니다.**

획득 경로:
- 미션 완료: 10 별조각/회 (일 15회 제한 = 150)
- 공유 보상: 10 별조각/회 (일 1회 제한 = 10)
- 출석 보상: 5 별조각/일 (향후)
- **일일 최대 획득**: 약 160 별조각

소비 경로:
- 밥 주기: 3 별조각/회
- 놀아주기: 2 별조각/회
- 스킨: 50~100 별조각
- 배경: 80~150 별조각
- 소모품: 5~10 별조각

밸런스 예시:
- 일일 돌봄 비용: 약 15 별조각 (밥 3회 + 놀아주기 3회)
- 일일 순수익: 145 별조각
- 스킨 구매 주기: 약 1주일

### 근거

1. **지속 가능성**: 매일 플레이하면 1주일에 스킨 1개 구매 가능
2. **목표 제공**: 스킨/배경 수집이라는 장기 목표
3. **과금 여지**: 향후 별조각 구매 옵션 추가 가능
4. **유연성**: 밸런스 조정 용이 (보상/비용 변경)

### 결과 (긍정)

- ✅ 적절한 도전 과제 제공
- ✅ 장기 플레이 유도
- ✅ 과금 모델 확장 가능
- ✅ 밸런스 조정 용이

### 결과 (부정/리스크)

- ⚠️ 밸런싱 지속적인 모니터링 필요
- ⚠️ 사용자 피드백에 따라 조정 필요
- ⚠️ 인플레이션 관리 필요

### 재검토 조건

- 사용자 이탈률이 높을 시 (너무 엄격)
- 스킨 구매 후 이탈률이 높을 시 (너무 관대)
- 평균 플레이 시간이 목표치를 벗어날 시

## ADR-012: 공유 카드 링크 생성 주체

**상태**: Accepted

**날짜**: 2026-05-14

### 컨텍스트

캐릭터 카드 공유 시 공유 링크를 누가 생성할지 결정해야 합니다.

### 고려한 대안

#### A. Gateway Module에서 생성
- **장점**: 중앙 집중식 관리
- **단점**: Gateway의 책임 과다, Character 도메인 로직 분산

#### B. Character Module에서 생성
- **장점**: 도메인 로직 집중, 캐릭터 데이터 접근 용이
- **단점**: Character Module 책임 증가

#### C. 별도 Share Module 생성
- **장점**: 공유 로직 독립 관리
- **단점**: 모듈 수 증가, MVP에 과도한 복잡도

### 결정

**Character Module에서 공유 카드 생성 및 링크 관리를 담당합니다.**

Character Module 책임:
- 공유 카드 이미지 생성
- 공유 링크 생성 (`https://polaris.app/share/{shareCardId}`)
- 공유 이벤트 기록
- 공유 보상 지급 (User Module 호출)

테이블:
- `share_cards`: 생성된 공유 카드
- `share_events`: 공유 이벤트 기록
- `referrals`: 추천인 추적

### 근거

1. **도메인 응집도**: 캐릭터 카드는 캐릭터 도메인의 일부
2. **데이터 접근**: 캐릭터 데이터에 직접 접근 가능
3. **단순성**: 별도 모듈 생성 불필요
4. **확장성**: 향후 공유 기능 확장 시 Character Module 내에서 관리

### 결과 (긍정)

- ✅ 도메인 로직 집중
- ✅ 캐릭터 데이터 접근 용이
- ✅ 모듈 수 최소화
- ✅ 구현 단순

### 결과 (부정/리스크)

- ⚠️ Character Module 책임 증가
- ⚠️ 공유 기능이 복잡해지면 분리 필요

### 재검토 조건

- 공유 기능이 과도하게 복잡해질 시
- 다른 도메인(미션, 아이템 등)에서도 공유 기능이 필요해질 시

## 🔄 ADR 프로세스

### ADR 작성 시점
- 중요한 아키텍처 결정을 내릴 때
- 여러 대안 중 하나를 선택할 때
- 향후 재검토가 필요한 결정일 때

### ADR 상태
- **Proposed**: 제안됨 (검토 중)
- **Accepted**: 승인됨 (적용 중)
- **Deprecated**: 폐기됨 (더 이상 사용 안 함)
- **Superseded**: 대체됨 (다른 ADR로 대체)

### ADR 재검토 프로세스
1. 재검토 조건 발생 확인
2. 현재 결정의 문제점 분석
3. 새로운 대안 검토
4. 팀 논의 및 합의
5. 새 ADR 작성 (기존 ADR은 Superseded 처리)
